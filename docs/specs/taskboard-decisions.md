`docs/specs/taskboard.md` の付属ファイル。**仕様の正本は spec 本体**で、ここは
「なぜその仕様にしたか」「何を不採用にしたか」の記録。

- 分離した理由: spec 本体が 1,887 行になり、Cursor が1つの変更のために読む量が
  大きくなっていたため（2026-08-07 のリファクタ監査 R3-2）。
  **その後の機能追加で本体は再び 1,900 行超（2026-08-18 時点 1,971 行）**。
  分離は「決定の記録を分けた」効果が本体で、行数削減の効果は続いていない
  （再分割はしない — 分ける軸が無く、探す場所が増えるだけ）
  **`docs/specs/` 直下に置く**のは、`test/run` の文字チェック対象が
  `docs/specs/*.md`（非再帰）でサブディレクトリだと静かに外れるため（R3-4）
- 追記の作法: 承認を得た Phase ごとに1セクション。**TB-Q<番号>** で採否と理由を残す。
  不採用にした案も理由付きで残す（後から同じ議論を繰り返さないため）
- テストケースと手動スモーク項目は spec 本体にある
- **TB-Q10 と TB-Q11 はこのファイルに無い**（分離で失われたのではなく、元から
  決定事項セクションに書かれていなかった）。それぞれ spec 本体の該当箇所に直接ある:
  TB-Q10 = アーカイブ先の確実な検出（`showDirectoryPicker` 案・**未実装の要確認**）、

## 決定事項（Phase I・IME と取り消し・2026-08-05 承認）

- **TB-Q6**: 誤追加の根本原因への対処 → **決定: `isComposing` ガード（3箇所）＋ `keyCode === 229` 併用**。
  対象は `#add-content` / 子タスク popover / インライン編集の3つの Enter ハンドラ
  - 不採用①「トリガーを `Cmd/Ctrl+Enter` に変更」: **保存が既に Cmd+S** のため、追加まで修飾キーに
    すると修飾キー操作が2種類並ぶ。`Enter=追加` / `Cmd+S=保存` の操作モデルの方が素直
    （リポジトリ全体の Cmd+Enter 慣習より、このツール内の一貫性を優先する — ユーザー判断）
  - 不採用②「Enter での追加をやめてボタンのみ」: 最頻ツールの入力速度が落ち、
    キーボード導線を足した ux-backlog CM-3 の方針に逆行する
- **TB-Q7**: 追加後のフォーカス → **決定: `#add-content` に戻す**（連続追加を自然にする。
  ボタンにフォーカスが残る現状の副作用を消す）
- **TB-Q8**: 誤追加の取り消し → **決定: `orig === null` の追加行限定＋挿入された空行も同時に取り消す**。
  `{type:'undoAdd', line}` として既存の op エンジンに載せ、`applyOps` でバイト同一性を照合する
  - 子孫を持つ追加行は取り消し不可（部分木の削除は「削除機能」になるため）
  - 不採用「1段 undo（`Cmd+Z`）」: 期限・優先度・完了も救えるが範囲が広く、
    今回の症状に対して過剰。「どこまで戻るか」が見えにくく多段化の圧力もかかる
  - 不採用「現状の周知のみ（保存前なら再読込で破棄できる）」: 実装ゼロだが**全変更が消える**ため、
    朝の計画を一通り入れた後には使えない
- **TB-Q9**: **Escape の IME ガード** → **決定: Phase I に含める**。
  `document` の Escape ハンドラ（`closePopover`）は変換中でも発火するため、
  **子タスク popover で変換候補を戻そうと Escape を押すと popover が閉じて入力が失われる**。
  変換候補を戻すための Escape は IME 利用者の日常的な操作であり、原因・対処・テスト方法が
  すべて既存の枠と同一なので除外する理由がない（ユーザー判断）。
  対処は他の3箇所と同じ1行（`if (e.isComposing || e.keyCode === 229) return;`）

## 決定事項（Phase T2・ステータスの3値化とボードの列切替・2026-08-06 承認）

- **TB-Q38**: 記法 → **決定: Obsidian Tasks の標準に従う**（`[ ]` / `[/]` / `[x]`）。
  独自記法は発明しない。`[/]` は Tasks の**既定のカスタムステータス**（型 `IN_PROGRESS`）で、
  仮に設定から外していても **Unknown = 型 `TODO`** として "not done" に一致するため、
  どちらに転んでも「着手中は未完了」が Obsidian 側と食い違わない（Phase 0 の一次情報確認）
- **TB-Q39**: `TASK_RE` の括弧内 → **決定: 任意の1文字 `(.)` に広げる**。
  未知の記号もタスク行として**表示し保全する**（従来はパススルーで画面に出なかった）。
  代わりに**状態を決める場所を `statusOf` の1箇所に固定**し、`done` をそこから派生させる
  - **これが本バッチの最重要点**: `TASK_RE` だけ広げて `done`（`m[2] !== ' '`）を直さないと
    着手中が完了扱いになり、**アーカイブで tasks.md から静かに消える**
- **TB-Q40**: 未知の記号（`[-]` `[?]` 等）→ **決定: 「不明」＝未完了として扱い、
  こちらから書き換えない**。アーカイブ対象にもしない（安全側）。
  **Tasks の既定設定では `[-]` = `CANCELLED` = "done" に一致するので、ここは意図的な差異**
  → 「ステータス仕様 / 既知の差異」
- **TB-Q41**: `[X]`（大文字）→ **決定: 従来どおり完了として読み、原文を保持する**。
  同じ状態への `setStatus` は何もしないので `x` に矯正されない
- **TB-Q42**: リストの操作口 → **決定: チェックボックスは残し、状態バッジを1つ足す**
  （バッジクリックで3択）。チェックボックスは「完了/未完了」の最頻操作、
  バッジは「着手中に落とす」操作。**着手中からのチェックは完了になる**
- **TB-Q43**: ボードの列 → **決定: セクション / ステータス / 優先度 の3択の `<select>`**。
